## 1. Как устроен код — простыми словами

У приложения три части:

- `android/app` — то, что видит человек: кнопки, поля, карточки, переходы. `Screen` рисует экран. `ViewModel` помнит его состояние: вопрос, выбранные карты, ожидание ответа и ошибки.
- `android/domain` — общие понятия: карта, расклад, баланс. Здесь описано, какие действия приложение умеет выполнять.
- `android/data` — получение данных по интернету и сохранение на телефоне. `Repository` связывает экран с API и локальной базой.

API — серверная программа, с которой общается телефон. Это `app_api_server.py`. Она получает толкование, проверяет баланс и хранит историю в отдельной PostgreSQL `app_bot_db`. Ключ DeepSeek остаётся на сервере.

Room — библиотека для маленькой базы внутри телефона. Она сохраняет список истории, открытые результаты и последний загруженный профиль. Она не заменяет сервер: новые расклады и уточнения требуют интернета. Изображения загружает и кэширует Coil; если изображения ещё нет в кэше и сеть недоступна, видно название карты.

Источники по библиотекам: [Room](https://developer.android.com/training/data-storage/room), [Coil Compose](https://coil-kt.github.io/coil/compose/). В проекте закреплены Room 2.6.1 и Coil 2.7.0, совместимые с существующим стеком; весь Android-проект на новые версии не переводился.

## 2. Что происходит на каждом экране

### Расклад

1. Человек вводит вопрос. Пустой вопрос отправить нельзя; ограничение — 1000 символов.
2. Выбирает «Карты сами» или «Выбрать самой».
3. В ручном режиме сервер выдаёт 9 случайных разных карт. Пока не нажали, они закрыты рубашкой. Нужно выбрать 3 карты; нажатие переворачивает карту, повторное нажатие снимает выбор.
4. Порядок выбора задаёт позиции: прошлое, настоящее, будущее.
5. Кнопка «Получить толкование» отправляет вопрос. Пока сервер отвечает, повторная отправка заблокирована. Ожидание может занять до 90 секунд; Android ждёт ответ до 120 секунд. В xTunnel также установлен `--backend-timeout 120`; полный сценарий с долгим ответом ещё нужно проверить на живом API.
6. Сервер сохраняет расклад и уменьшает баланс одной транзакцией. Это означает: либо успешно сохраняются оба изменения, либо ни одно. Если DeepSeek не ответил, баланс не уменьшается.
7. Если связь оборвалась после отправки, «Повторить запрос» использует прежний идентификатор запроса. Сервер возвращает уже готовый результат, если он успел его сохранить. Дополнительный расклад не расходуется. До разрешения такого запроса его вопрос и карты зафиксированы.
8. Если расклады закончились, открывается магазин. **Результат последнего бесплатного расклада показывается полностью** — его не перекрывает магазин.

Вопрос, режим, колода и выбранные карты сохраняются в состоянии Android. Незавершённый запрос можно повторить после пересоздания процесса. При повторном открытии через значок после принудительной остановки Android может не восстановить экран; готовый результат остаётся на сервере в истории.

### Результат и уточнения

Показываются три изображения, названия карт и текст. Старые HTML-теги из толкования не выводятся буквально. Текст можно выделить и скопировать.

Для бесплатного расклада доступно 2 уточнения, для платного/безлимитного — 5. Лимит проверяет сервер. Вопросы и ответы сохраняются вместе с раскладом. Неудачный запрос не уменьшает счётчик; повтор после обрыва сети использует тот же идентификатор.

### История

Список загружается с сервера и сохраняется в Room. Нажатие открывает полный расклад. «Загрузить ещё» запрашивает следующую страницу: история не ограничена первыми 20 записями.

Без сети можно читать уже сохранённый список и те полные результаты, которые ранее создавались или открывались на этом телефоне. Для первого открытия другого старого расклада нужен интернет. При сетевой ошибке сохранённый список остаётся виден.

Ранее созданный гость может войти в приложение без сети и прочитать кэш. **Самый первый запуск** всё равно требует интернета для создания гостя.

### Профиль

Показывает бесплатные и купленные расклады, активный безлимит и общее число раскладов. Сохранённый баланс явно помечается, если сервер недоступен.

Обратная связь отправляется в `app_feedback` отдельной базы приложения. Сообщение ограничено 2000 символами. Автоматической пересылки в Max/почту в этом этапе нет; интерфейс сообщает, что сообщение сохранено для поддержки.

«Удалить мои данные» сначала показывает подтверждение. После подтверждения API удаляет гостя и связанные записи: историю, уточнения, баланс, сообщения обратной связи и токены. Затем телефон очищает локальную базу и сессию, приложение возвращается к онбордингу. Старый токен больше не даёт доступ к данным. Если сервер не подтвердил удаление, локальные данные сохраняются, запрос можно повторить.

Кнопок регистрации, входа и привязки Max нет.

### Магазин

Пакеты и цены поступают из API. После выбора пакета открываются способы «Оплатить в RuStore» и «Оплатить картой (ЮKassa)». Для консультации доступна только ЮKassa.

Это вёрстка этапа 4: нажатие на оплату объясняет, что покупки пока недоступны. Платёж не создаётся, деньги не списываются, баланс не пополняется.

«Написать Диане» открывает HTTPS-ссылку из `APP_TAROLOGIST_PROFILE_URL`. Если ссылка не задана, показывается понятное сообщение. Эта кнопка открывает контакт и сама ничего не отправляет.

## 3. Почему понадобились изменения сервера

На этапе 3 в API не было уточнений, обратной связи и удаления. Для работающих экранов добавлены:

| Запрос | Назначение |
|---|---|
| `GET /v1/tarot/deck` | 9 разных карт для ручного выбора |
| `POST /v1/divinations/tarot` | Расклад; добавлен `request_id` для безопасного повтора |
| `GET /v1/divinations/{id}` | Полный результат с уточнениями и остатком лимита |
| `POST /v1/divinations/{id}/follow-up` | Уточнение с `question` и уникальным `request_id` |
| `GET /v1/me/history?before_id=…` | Следующая страница истории |
| `POST /v1/me/feedback` | Обратная связь: `{"message":"…"}` |
| `DELETE /v1/me` | Удаление данных текущего гостя |
| `GET /v1/catalog` | Пакеты, консультации и контакт Дианы |

Все запросы работают с гостевым токеном. История и уточнения ищутся одновременно по id расклада и id гостя — чужой результат прочитать нельзя.

Развёртывание кода и миграция завершены. Повторно применять миграцию сейчас не требуется. Команда ниже сохранена для новой VM или восстановления; миграция идемпотентна и затрагивает только отдельную базу приложения:


На сервере осталось:

1. Задать настоящий контакт Дианы:


4. До публикации решить, будет ли перезапуск `app-api` и применение миграций отдельным workflow или останутся ручной операцией. Текущий workflow Max перезапускает только `max-bot.service`.

## 5. Как собрать и установить APK

APK — файл установки Android-приложения. **Актуальная сборка от 20 сентября содержит постоянный адрес, исправления кнопок и название «Сфера Таро».** Debug APK предназначен для разработки, а не для публикации в RuStore.

Артефакт: [`android/app/build/outputs/apk/debug/app-debug.apk`](../android/app/build/outputs/apk/debug/app-debug.apk), версия `0.4.0-debug`, размер около 19 МиБ. SHA-256 актуальной локальной сборки:

```text
df166419a5fb4c5f37d10965843ab314b941023bd93e49285c6cd738b29f9b2a
```

Ниже — команды для повторной сборки после изменений и установка:

1. Открыть в Android Studio папку `android`, дождаться Gradle Sync.
2. По умолчанию в `android/data/build.gradle.kts` уже задан постоянный URL. Если в локальном `~/.gradle/gradle.properties` осталась настройка прежнего туннеля, обновить её или передавать новый адрес явно в команде сборки:

   ```properties
   APP_API_BASE_URL=https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com/
   ```

   Создавать локальное переопределение не обязательно. Параметр `-PAPP_API_BASE_URL=…` ниже имеет приоритет над ним. URL обязательно HTTPS, без `/v1`.

3. Для сборки и всех локальных Android-проверок выполнить из корня `max_bot`:

   ```bash
   bash scripts/check_android.sh -PAPP_API_BASE_URL=https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com/
   ```

   Скрипт использует установленную на этом Mac Java 22. Java 25, встроенная в текущую Android Studio, несовместима с Gradle 8.11.1. При сборке через Studio выберите совместимую Gradle JDK в Settings → Build, Execution, Deployment → Build Tools → Gradle. На другом компьютере можно передать путь: `ANDROID_JAVA_HOME=/путь/к/jdk bash scripts/check_android.sh` (JDK 17–23).

4. Готовый файл: `android/app/build/outputs/apk/debug/app-debug.apk`.
5. Для первой установки передать APK через почту, мессенджер, облако или кабель, открыть файл и временно разрешить этому источнику установку неизвестных приложений. Для обновления установить новый APK поверх предыдущей debug-версии с той же подписью, не удаляя приложение: гость, баланс и история сохранятся. Альтернатива — подключить телефон с USB-отладкой и выполнить установку через Android Studio/ADB.

В APK проверено наличие постоянного URL в DEX и отсутствие прежнего тестового адреса. `apksigner verify` подтвердил подпись по схеме v2. Первая версия уже установлена на телефон; свежую сборку с исправлениями нужно установить поверх неё и продолжить сценарии ниже.

## 8. План визуального редизайна

Три концепции, аудит и точные Compose-токены находятся в [отдельном дизайн-брифе](ANDROID_REDESIGN.md). Рекомендуемое направление — **«Лунный атлас»**.

### 8.1. Цель и направление

Текущая версия функциональна, но первая проверка на реальном телефоне показала, что системные компоненты и общая типографика ещё не образуют законченную визуальную систему. Выбранное направление: **современная мистическая редакционная эстетика** — спокойная, взрослая и читаемая, без перегруженного эзотерического декора.

- глубокий тёмный фон с очень мягкой фактурой или градиентом;
- тёплое золото только для акцентов и действий;
- бордовый как дополнительный цвет;
- выразительная кириллическая гарнитура для заголовков и простая гарнитура для длинного текста;
- лёгкие поверхности и карточки вместо одинаковых массивных рамок;
- ясные состояния: активно, выбрано, недоступно, загрузка и ошибка.

### 8.2. Порядок работы

1. Собрать референсы и сделать 2–3 статичных варианта ключевого экрана. Для анализа, UX и реализации использовать GPT-6 Astra; для иконки, фона и декоративных ассетов — GPT-Image-2.5 Sunburst.
2. Выбрать один вариант до изменения всех экранов.
3. Зафиксировать Compose-токены: палитру, типографику, сетку отступов, радиусы, высоты элементов и состояния компонентов.
4. Сначала реализовать онбординг, экран вопроса и результат как вертикальный срез; проверить на телефоне.
5. После подтверждения перенести систему на историю, магазин и профиль.
6. Добавить только полезные анимации: переворот карты, появление результата и переход в историю.
7. Пересобрать APK, пройти Lint/тесты и весь чек-лист §6.

### 8.3. Обязательные UX-проверки

- текст на активных и неактивных кнопках имеет достаточный контраст;
- кнопки и переключатели имеют зону нажатия не меньше 48 dp;
- при крупном системном шрифте текст не обрезается и экраны прокручиваются;
- клавиатура не закрывает поле и основное действие;
- ручной выбор трёх карт понятен без инструкции;
- ожидание ответа до 120 секунд объяснено и не выглядит как зависание;
- навигация, ошибки, повтор запроса и офлайн-состояние визуально различимы;
- иконка читается на светлом и тёмном launcher-фоне;
- изображения, созданные генеративной моделью, используются как ассеты, а интерфейс и текст остаются нативными Compose-компонентами.

### 8.4. Критерий завершения

Редизайн завершён, когда свежий APK прошёл автоматические проверки, все экраны проверены на реальном телефоне с обычным и крупным шрифтом, а минимум 5 тестировщиков самостоятельно проходят путь «онбординг → вопрос → выбор карт → результат → история» без подсказок.
