# Защита стартового подарка Android

Реализация в `app/trial_grants.py`, вызывается внутри транзакции регистрации
для логина/пароля, подтверждённой почты и VK ID. Android-клиент продолжает
передавать `device_signal` и читать баланс из существующего API; обновление APK
для этих серверных ограничений не требуется.

## Поведение

- Один стартовый пакет из 3 раскладов на идентификатор устройства. История
  `app_trial_claims` переживает удаление аккаунта (`ON DELETE SET NULL`).
- Сохраняется каждый идентификатор входа, в том числе при отказе из-за уже
  использованного устройства. Удаление такого аккаунта и повторная регистрация
  на другом устройстве не дают подарок.
- Пустой, пробельный, нестроковый, нулевой или некорректный `ANDROID_ID` не даёт
  подарок. Принимается шестнадцатеричная строка длиной 1–16 символов, регистр и
  внешние пробелы нормализуются. Известный общий ID `9774d56d682e549c` исключён.
  Регистрация и вход остаются доступны; `trial_granted` равен 0.
- Старый аккаунт без записи в журнале, привязка способа входа и конвертация
  staging-гостя не увеличивают бесплатный баланс.
- Проверка устройства, запись идентификатора, проверка общего лимита и начисление
  выполняются в одной транзакции под общей блокировкой PostgreSQL. Это действует
  между процессами API и разными способами регистрации. При откате подарок
  не считается выданным.
- `APP_TRIAL_DAILY_LIMIT=1000` — максимум новых пакетов за скользящие 24 часа
  во всём окружении. Это начальное техническое ограничение, его нужно подобрать
  под допустимые расходы и реальные регистрации. `0` выключает новые подарки.
  Отрицательные значения не позволяют API стартовать.
- Отказ не меняет имеющийся бесплатный или оплаченный баланс и не блокирует
  обычный вход. Отказ записывается окончательно: автоматического доначисления
  на следующий день нет. При восстановлении лимита подарки получают только
  новые допустимые регистрации; поддержка может отдельно компенсировать отказ.

Лимит ограничивает выдачу новых бесплатных обязательств (1000 пакетов = 3000
раскладов), а не фактические расходы LLM за сутки: ранее начисленные расклады
можно использовать позже. Он не является денежным лимитом провайдера LLM.

## Развёртывание

1. На время миграции и смены версии остановить API приложения, чтобы старый
   процесс не создавал новые пропущенные записи. Применить
   `app/migrations/009_trial_grants.sql` к нужной БД приложения перед
   обновлением API. Миграция добавляет индекс и заполняет пропущенные старым кодом
   идентификаторы без начисления баланса. Повторное применение безопасно.
2. Выбрать `APP_TRIAL_DAILY_LIMIT` в конфигурации каждого окружения отдельно.
3. Обновить API, выполнить smoke: новый аккаунт получает 3, другой аккаунт на
   том же устройстве — 0; после удаления второго аккаунта и смены устройства
   повторный подарок не появляется. Проверить обычный вход аккаунта модератора.
4. Наблюдать журнал: `Welcome gift granted` и `Welcome gift denied: reason=...`.
   Причины: `device_used`, `invalid_device`, `existing_account`, `daily_limit`.
   Достижение общего лимита пишется с уровнем WARNING; остальные события — INFO.
   Отправка внешних уведомлений этим изменением не подключается.

Существующие ограничения попыток парольной регистрации по IP сохраняются.
Новые жёсткие ограничения подарков по IP не добавлены: за xTunnel сервер может
видеть общий адрес прокси. Нельзя доверять произвольному `X-Forwarded-For`.
Подключение CAPTCHA и проверку подлинности устройства следует делать отдельно,
с выбранным провайдером и проверенной поддержкой RuStore/устройств без Google.

## Ограничения и хранение

`ANDROID_ID` — сигнал устройства, а не доказательство личности. Другой профиль
Android, сброс телефона или подмена запросов могут обойти эту часть защиты;
проверка формата не является проверкой подлинности. Общий бюджет ограничивает
масштаб новых начислений даже при подмене. Один телефон может использовать семья:
отказ относится только к подарку, а не к аккаунту или покупкам.

Хеши устройства используют существующий HMAC с `APP_JWT_SECRET`. Смена этого
секрета меняет хеши: ротацию нужно планировать вместе с переносом защиты, нельзя
считать историю устройств сохранённой после простой замены ключа. Сырые ID и
логины не выводятся в новые операционные сообщения.

Политика хранения `app_trial_claims` этим изменением не меняется. Срок хранения
и описание антифрод-учёта после удаления профиля необходимо согласовать в
публикуемой политике данных. Автоматическое удаление журнала вернёт возможность
получать подарок по забытым идентификаторам. Не очищать его для сброса лимита.

## Проверки

`tests/test_password_auth.py` содержит проверки с настоящим PostgreSQL: гонки
между способами входа, общий бюджет и его окно, удаление/повторная регистрация,
невалидные ID, откат транзакции, миграция и сохранность оплаченного баланса.

```sh
PASSWORD_TEST_DSN='postgresql://USER@localhost:PORT/postgres' \
  venv/bin/python -m unittest discover -s tests -v
```

Использовать только отдельный локальный PostgreSQL. Тесты создают и удаляют
собственные случайные схемы. Без `PASSWORD_TEST_DSN` интеграционные тесты
пропускаются; модульные проверки выполняются.
