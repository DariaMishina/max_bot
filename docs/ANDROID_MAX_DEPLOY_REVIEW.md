## Разделение приложения и бота

- `01ca2fe` добавляет Android-проект, отдельный workflow сборки и правила игнорирования файлов. Сборка Android выполняется на GitHub runner, не на VM бота.
- `d01a028` исправляет Android-клиент, восстановление гостя в `app/database.py` и тестовый скрипт приложения. Бот не импортирует `app/database.py`.
- Текущие изменения API используют отдельные настройки `APP_DB_*` и таблицы `app_*` в `app_bot_db`. Автодеплой не запускает `init_app_db.sql` или `app/migrations/004_mvp.sql`.
- Служба xTunnel направляет трафик на порт `8083`, а не на webhook бота `8081`. Её ключ находится вне репозитория. Автодеплой Max не устанавливает и не перезапускает `xtunnel-app`.
- В `send_message.py` изменён только CLI `main()`: добавлен флаг `--back-to-menu` для ручного `--text`. Все остальные 25 функций совпадают с базовым коммитом по AST, включая функции напоминаний, импортируемые ботом. Без нового флага клавиатура остаётся `None`.

## Что исправлено в workflow деплоя

В прежнем `.github/workflows/deploy.yml` любой пуш в `main` запускал переустановку зависимостей и перезапуск Max. Ошибка проверки сервиса скрывалась через `|| true`, после чего печаталось сообщение об успешном деплое.

В текущем коммите:

1. Добавлен фильтр файлов бота: `bot.py`, `webhook_server.py`, `send_message.py`, `main/**`, `handlers/**`, `keyboards/**`, `static/**`, `requirements.txt` и сам workflow. Последующие изменения только Android, `app/**`, документации или тестов не запустят деплой Max.
2. При существующем venv и неизменном `requirements.txt` зависимости сохраняются. При новом venv или изменении требований выполняется `python -m pip install -r requirements.txt`. Автоматическое обновление самого pip убрано.
3. После перезапуска неактивный `max-bot.service` завершает workflow с ошибкой; сообщение об успешном деплое не печатается.

Для проверенной серии `requirements.txt` не изменён. На VM установлен `aiomax 2.12.5`; данный деплой не должен менять его при сохранении текущего venv.

## Что остаётся после пуша

После будущего деплоя нужно проверить живые `/start`, расклад и оплату в Max. Локальные проверки не доказывают доступность внешних Max/DeepSeek/ЮKassa в момент запуска.

Для Android отдельно требуется применить `004_mvp.sql` к **`app_bot_db`** перед запуском обновлённого `app-api`. Workflow Max обновит файлы общей рабочей копии, но не применит эту миграцию и не перезапустит API приложения. Новый API нельзя считать развёрнутым только потому, что деплой бота завершился успешно. Порядок обновления — в [руководстве этапа 4](ANDROID_STAGE4_GUIDE.md).
