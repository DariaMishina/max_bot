# План: Android-приложение «Сфера Таро» (только RuStore)

Отдельное приложение для Android на базе логики чат-бота в Max. Бот **не ломаем** и **не связываем** с приложением в первой версии.

Приложение — не окно в Max и не сайт в браузере, а обычная программа с иконкой на телефоне. Ставят из **RuStore**.

---

## Зафиксированные решения

| Вопрос | Решение |
|--------|---------|
| Отображаемое название и название в RuStore | **Сфера Таро** |
| `applicationId` / package name | **`ru.tarotsphere.app`** |
| Платформа | Только Android |
| Язык приложения | Kotlin + Jetpack Compose |
| Магазин | Только **RuStore** (Google Play — не делаем) |
| Оплата в приложении | Две опции на экране оплаты: **RuStore Pay SDK** и **ЮKassa** |
| База данных | **Отдельная** PostgreSQL, не таблица бота |
| Регистрация | **Обязательна перед первым раскладом:** **VK ID** или **код на email**, без отдельного логина и постоянного пароля |
| Основной вход | **VK ID** через официальный SDK; запасной способ — одноразовый код на подтверждённую почту |
| Идентификация устройства | `ANDROID_ID` только как дополнительный антифрод-сигнал, не как аккаунт и не как единственный способ входа |
| Дополнительные входы позже | Яндекс ID — не в первой production-версии |
| Связка с аккаунтом бота Max | **Не делаем** (бэклог) |
| iOS / Flutter | Не делаем |
| HTTPS для API приложения | **[xTunnel](https://xtunnel.ru/)** — свой домен **не покупаем**. Пользователи URL **не видят** |
| Cloudflare | Только для **WebApp** бота (порт 8081). Для Android **не обязателен** |

Бот в Max живёт как сейчас: свои пользователи, свой баланс, своя ЮKassa. Покупка в боте **не** появится в приложении, и наоборот. Это ожидаемо, пока нет связки.

## 2. Как это устроено

```
  Бот Max                    Приложение Android
  (как сейчас)               (Kotlin, иконка на телефоне)
       │                              │
       ▼                              ▼
  БД бота                      БД приложения
  max_bot_db                   app_bot_db   ← новая, отдельная
       │                              │
       │                         Backend API
       │                      (HTTPS, свой процесс)
       │                              │
       └──────── DeepSeek, картинки карт ────────┘
                 (общий смысл логики, разные данные)
```

Код толкования (промпты, колода, пакеты) лучше **переиспользовать** из Python-сервиса, чтобы тексты раскладов не разъехались. Данные — **разные базы**.

Клиент на телефоне **никогда** не ходит в DeepSeek, ЮKassa API и PostgreSQL сам. Только в наш HTTPS API.

### 2.3. Кто такой пользователь приложения

В Max идентификатор даёт мессенджер. В Android-приложении создаётся собственный `user_id`, к которому привязывается хотя бы один подтверждённый способ входа.

После онбординга показывается единый экран **«Войти или создать аккаунт»**:

- основная кнопка — **«Продолжить через VK ID»**;
- запасной способ — **«Продолжить по email»**, отправка и ввод одноразового кода;
- отдельных вкладок «Регистрация» и «Вход» нет: сервер сам определяет, новый это идентификатор или существующий;
- постоянных паролей, логинов и восстановления пароля нет.

| Когда | Что происходит |
|-------|----------------|
| Новый VK ID или подтверждённый email | Создаётся аккаунт, один раз выдаются 3 бесплатных расклада |
| Повторный вход | Открывается тот же `user_id`, баланс и история сохраняются |
| Новый телефон | После VK ID или email-кода восстанавливается тот же аккаунт |
| Добавлен второй способ входа | VK ID и email указывают на один `user_id`; второй подарок не выдаётся |
| Выход | Локальные токены очищаются, серверные баланс и история остаются |
| Удаление аккаунта | Пользовательские данные удаляются; повторная регистрация не должна автоматически возвращать пробный подарок |

Текущий автоматический `/auth/guest` нужен только для существующей debug-версии и тестового перехода. В production новый анонимный гость не получает баланс и не может выполнять расклады или покупки.

## 3. API приложения

Префикс API: `https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com/v1/`. В `APP_API_PUBLIC_URL` серверного `.env` и `BuildConfig.API_BASE_URL` Android задаётся адрес без `/v1`; пути методов добавляет клиент.

Отдельный процесс, например `app_api_server.py`, порт не 8081 (у бота webhook). Не смешивать с `bot.py`.

Access-токен обязателен для запросов к данным пользователя. Исключения: начало/подтверждение входа, обновление сессии, `/health`, `/v1/docs` и изображения `/static/`. `user_id` определяется только из проверенного сервером токена.

**Статус API на 2026-09-24:** методы экранов MVP развёрнуты на сервере и доступны через постоянный xTunnel. После применения `004_mvp.sql` и перезапуска `app-api` пройден живой сценарий гость → баланс → расклад DeepSeek → история. Этот гостевой сценарий остаётся для тестирования; VK ID, email-коды, пуши, Ицзин, карта дня и платёжные методы ниже ещё не реализованы.

### 3.1. Сессия

| Метод | Путь | Зачем |
|-------|------|--------|
| POST | `/auth/vk` | Принять результат VK ID, проверить его на сервере, войти или создать аккаунт |
| POST | `/auth/email/start` | Отправить одноразовый код; ответ не раскрывает, существует ли аккаунт |
| POST | `/auth/email/confirm` | Проверить код, войти или создать аккаунт |
| POST | `/auth/refresh` | Обновить токен |
| POST | `/auth/logout` | Отозвать refresh-токен текущего устройства |
| POST | `/auth/link/vk` | Привязать VK ID к уже вошедшему аккаунту |
| POST | `/auth/link/email/start` | Начать привязку второго способа входа по email |
| POST | `/auth/link/email/confirm` | Подтвердить email и привязать его к текущему `user_id` |
| POST | `/auth/push-token` | Токен RuStore Push — ещё не реализован, этап 6 |

`/auth/guest` временно сохраняется только в staging для проверки уже реализованного приложения. Перед production он не должен выдавать пробный баланс анонимному запросу.

Для email-кода: 6 цифр, срок действия 10 минут, одно использование, не больше 5 попыток ввода; повторная отправка не раньше чем через 60 секунд. Нужны лимиты по email, IP и сигналу устройства. Коды и полные адреса не писать в журналы.

Для VK ID приложение получает результат официального SDK и передаёт его серверу; сервер проверяет токен у провайдера и только затем доверяет `provider_user_id`. Не принимать VK ID обычной строкой из тела запроса.

Правило связывания: один `provider_user_id` принадлежит только одному `user_id`. Если идентификатор уже занят другим аккаунтом, показать ошибку и не объединять балансы автоматически. Для текущих тестеров первый подтверждённый вход может преобразовать существующего staging-гостя в аккаунт без потери истории; в чистом production аккаунт создаётся только после подтверждения VK ID или email.

**Нет** `/auth/link/max`. Яндекс ID и Google-вход в первую production-версию не входят.

### 4.1. `app_users`

Сервер создаёт пользователя после подтверждения VK ID или email:

- `user_id` UUID
- `is_guest` — `false` для production-аккаунтов; `true` остаётся только у старых staging-гостей на время перехода
- `created_at`, `last_active_at`
- `install_id` — старый случайный идентификатор debug-версии, не использовать как доказательство уникального пользователя

Email, VK ID и секреты входа не хранить непосредственно в `app_users`. Постоянных паролей нет.

### 4.1.1. `app_user_identities`

Один пользователь — несколько способов входа.

- `user_id`
- `provider`: в первой версии `vk` | `email`; позже можно добавить `yandex`
- `provider_user_id`: проверенный VK ID или нормализованный email
- `verified_at`, `created_at`
- UNIQUE (`provider`, `provider_user_id`) — один VK ID или email не должен принадлежать двум аккаунтам

Исходный вид email можно хранить для отображения и отправки кодов, а сравнение выполнять по единой заранее зафиксированной нормализации. В API и журналах адрес маскировать.

### 4.1.2. `app_email_codes`

Короткоживущие запросы входа по email:

- нормализованный email;
- хеш одноразового кода, но не сам код;
- срок действия, число попыток, время следующей разрешённой отправки;
- `used_at`, IP/риск-метаданные в минимально необходимом объёме;
- просроченные и использованные записи регулярно удаляются.

### 4.1.3. `app_trial_claims` и устройство

- Пробный пакет выдаётся только после первого подтверждённого входа.
- Один `user_id` получает 3 бесплатных расклада только один раз.
- Дополнительный ключ устройства строится на сервере как HMAC от `ANDROID_ID`; исходный идентификатор не используется как токен авторизации.
- Один и тот же аккаунт на новом телефоне восстанавливает старый баланс, но не получает новый подарок.
- Новый аккаунт на устройстве, уже получившем подарок, по умолчанию не получает второй пакет. Возможные ложные блокировки общего семейного телефона обрабатываются поддержкой.
- `ANDROID_ID` — только антифрод-сигнал: он не заменяет VK ID/email и не даёт доступа к аккаунту.

### 4.2. `app_user_balances`

Как у бота по смыслу: бесплатные, купленные, дата безлимита. В production новая строка начинается с **0**; после первого подтверждённого входа сервис `trial_claims` одной транзакцией начисляет **3 бесплатных**. Текущий debug-код, который создаёт баланс сразу с 3, нужно заменить на этапе 4.7.

### 4.3. `app_payments`

История: пакет, сумма, статус, `provider` (`rustore` | `yookassa`), внешний id платежа.

### 4.4. `app_divinations`

Вопрос, карты, толкование, дата. На этапе 4 добавлены `request_id` для безопасного повтора и `follow_ups` для уточнений. Эти поля появятся на действующем сервере после применения `app/migrations/004_mvp.sql`.

Обратная связь хранится в новой таблице **`app_feedback`** из той же миграции. Удаление аккаунта удаляет связанные пользовательские данные; отдельно определить минимальный срок хранения платёжных и антифрод-записей и описать его в политике.

### 4.5. `app_devices`

Токен пуша RuStore, пользователь/сессия и серверный HMAC от `ANDROID_ID` для антифрода. Исходный `ANDROID_ID` не хранить и не считать идентификатором аккаунта.

### 4.6. Чего нет в MVP

- Яндекс ID и входа через Max
- Таблиц связки с Max
- Кодов `/link`
- Записи в `max_users` / `max_user_balances`

### Этап 4.7. Авторизация VK ID + email-код (5–8 дней)

**Статус:** не начат. Это обязательная часть первой production-версии и должна быть готова до подключения боевых платежей.

#### Пользовательский сценарий

- [ ] После онбординга показать экран **«Войти или создать аккаунт»** в стиле «Тихая мастерская».
- [ ] Основное действие — **«Продолжить через VK ID»**.
- [ ] Второе действие — **«Продолжить по email»**: поле почты → отправка шестизначного кода → ввод кода.
- [ ] Не делать отдельные вкладки «Регистрация» и «Вход»: новый подтверждённый идентификатор создаёт аккаунт, существующий открывает его.
- [ ] Не добавлять логин, постоянный пароль и восстановление пароля.
- [ ] До входа разрешить онбординг и просмотр объяснения возможностей; расклад, история, покупки и подарок доступны только после входа.
- [ ] При повторном запуске с действующей сессией сразу открывать приложение; при истёкшем access-токене использовать refresh-токен.
- [ ] В профиле показывать привязанные способы входа, разрешить добавить второй способ и выполнить выход.

#### VK ID

- [ ] Зарегистрировать приложение в инструменте **VK ID** через RuStore Консоль и подключить официальный Android SDK ([документация RuStore](https://www.rustore.ru/help/sdk/vk-id)).
- [ ] Запрашивать только минимально необходимые данные; основным ключом считать стабильный идентификатор VK ID, а не имя или номер телефона.
- [ ] Передавать результат входа на сервер и проверять токен у провайдера. Не доверять `provider_user_id`, присланному обычной строкой с телефона.
- [ ] Обработать отмену входа, отсутствие приложения VK, браузерный сценарий и временную ошибку без потери уже существующей сессии.

#### Email-код

- [ ] Выбрать сервис доставки писем/SMTP, вынести ключи только на сервер и настроить адрес отправителя.
- [ ] Реализовать `/auth/email/start` и `/auth/email/confirm`; для привязки второго способа — отдельные защищённые методы `/auth/link/email/*`.
- [ ] Код: 6 цифр, срок 10 минут, одно использование, максимум 5 попыток, повторная отправка не раньше 60 секунд.
- [ ] Хранить только хеш кода; не писать код, токен и полный email в журналы.
- [ ] Возвращать одинаковый нейтральный ответ для нового и существующего адреса, чтобы посторонний не мог проверить наличие аккаунта.
- [ ] Ограничить отправку и проверку кодов по email, IP и сигналу устройства; предусмотреть понятное сообщение при задержке письма.

#### Аккаунт, подарок и переход со старого гостя

- [ ] Создать миграцию для `app_user_identities`, `app_email_codes`, `app_trial_claims` и серверного признака устройства.
- [ ] Выдавать 3 бесплатных расклада одной транзакцией только после первого подтверждённого входа; создание анонимного гостя больше не начисляет баланс.
- [ ] Гарантировать уникальность пары (`provider`, `provider_user_id`) и не объединять два существующих аккаунта автоматически.
- [ ] Разрешить одному `user_id` иметь VK ID и email; привязка второго способа не создаёт новый баланс и не выдаёт второй подарок.
- [ ] Добавить `ANDROID_ID` как дополнительный сигнал: на сервере хранить HMAC, а не использовать идентификатор как токен или самостоятельный аккаунт.
- [ ] По умолчанию выдавать не больше одного пробного пакета на подтверждённый аккаунт и устройство; вход существующего аккаунта на новом устройстве восстанавливает данные без нового подарка.
- [ ] Для текущей staging-версии предусмотреть одноразовое преобразование существующего гостя в подтверждённый аккаунт с сохранением истории и баланса. В чистом production анонимные данные не создаются.
- [ ] После удаления аккаунта не выдавать подарок повторно автоматически на тот же подтверждённый идентификатор/устройство; срок хранения минимальной антифрод-записи отразить в политике.

#### Проверки

- [ ] Новый VK ID → один аккаунт и 3 бесплатных; повторный вход → тот же аккаунт и тот же баланс.
- [ ] Новый email → письмо и один подарок; просроченный, неверный и повторно использованный код отклоняются.
- [ ] VK ID и email, привязанные к одному аккаунту, открывают одну историю и не дублируют подарок.
- [ ] Переустановка и новый телефон восстанавливают аккаунт после входа; новый UUID приложения не создаёт бесплатный баланс.
- [ ] Второй аккаунт на том же устройстве не получает ещё один подарок; срабатывание ограничения видно в журнале и объяснено пользователю.
- [ ] Выход отзывает refresh-токен только текущего устройства; удаление аккаунта лишает доступа все его сессии.
- [ ] Проверить крупный шрифт, маленький экран, клавиатуру, вставку кода из письма, отсутствие сети и повтор отправки.

**Готово, когда:** новый пользователь входит через VK ID или email-код, получает подарок ровно один раз, а повторный вход и вход на другом телефоне восстанавливают тот же баланс и историю. После этого платежи этапа 5 привязываются только к подтверждённому `user_id`.

## 6. Что в первой версии, что нет

**Делаем в MVP**

1. Онбординг, затем обязательный вход через VK ID или код на email.
2. Один аккаунт на разных телефонах: общий баланс и история.
3. Три бесплатных расклада один раз после первого подтверждённого входа.
4. Таро: вопрос, случайные или свои 3 карты.
5. Толкование с сервера.
6. Баланс и экран «купите пакет».
7. История.
8. Оплата: RuStore Pay и ЮKassa.
9. Выход и удаление данных с устройства / с сервера.
10. Политика конфиденциальности.

**Не делаем в MVP**

- Яндекс ID (этап 8)
- Вход через Max / привязка бота
- Google Play
- Общая БД с ботом
- Постоянный логин/пароль и восстановление пароля
- Подписка на канал Max как условие
- Ицзин, карта дня, фото-расклад — по остатку времени

## 8. Безопасность

1. Ключи DeepSeek, ЮKassa, секреты RuStore — только на сервере.
2. HTTPS + access/refresh-токены; `user_id` только из проверенного токена, не из тела запроса.
3. VK-токен проверяется сервером у провайдера; email-код одноразовый, короткоживущий и ограничен по попыткам.
4. Постоянные пароли не храним; коды, токены и полные email не пишем в журналы.
5. Списание баланса и выдача пробного пакета только на сервере и транзакционно.
6. Один внешний id платежа — одно начисление.
7. Вебхук ЮKassa бота и вебхук приложения — разные URL и разные БД.
8. Удаление аккаунта и отзыв всех его сессий из профиля.
9. `ANDROID_ID` — дополнительный антифрод-сигнал, а не секрет или способ авторизации.

## 14. HTTPS для API: xTunnel (без своего домена)

### Зачем это вообще

Приложение на телефоне **звонит на ваш сервер** по адресу `https://...`. Нужны:

1. **HTTPS** — иначе Android и оплата не работают нормально.
2. **Один и тот же адрес** — не меняется после перезапуска (для APK и webhook ЮKassa).

**Красивый домен пользователям не нужен** — URL вшит в код, в интерфейсе не показывается.

### Cloudflare — отдельная история

| | WebApp бота (браузер) | Android-приложение |

К Cloudflare **не привязаны**. Для приложения — **xTunnel**.

### Купленная лицензия xTunnel

19 сентября приобретена **Личная лицензия на месяц за 150 ₽**. Это цена покупки в кабинете пользователя; срок действия по кабинету — **до 19.10.2026**. Регистрация клиента на сервере подтвердила тариф **Personal**.

Свой домен у регистратора **не покупаем**: используется постоянный адрес xTunnel (`*.tunnel4.com`). Перед окончанием оплаченного периода нужно продлить лицензию для дальнейшей работы туннеля.

### Схема на VM

```
Android  →  https://....tunnel4.com/v1/...
                ↓
           xTunnel (на VM)
                ↓
      http://127.0.0.1:8083  ← app_api_server.py
                ↓
           app_bot_db
```

Порт **8083** — API приложения (`APP_API_PORT`). Порт **8081** — webhook бота / WebApp. Порт **8080** — psy_max.

### Текущая настройка туннеля (проверено 2026-09-19)

Базовый API проверен через постоянный HTTPS-адрес с Mac и с VM. После перезапуска туннеля адрес сохранился, внешний `/v1/docs` вернул тот же JSON, что локальный API. Обновление кода этапа 4 и миграция в ходе настройки туннеля не выполнялись.

| Параметр | Значение |
|----------|----------|
| Постоянный публичный URL | `https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com` |
| API на VM | systemd `app-api`, порт `8083`; `active`, `enabled` |
| xTunnel | Нативный Linux x64 клиент **4.0.0**, systemd `xtunnel-app`; `active`, `enabled` |
| Бинарный файл | `/home/dariamishina/.local/share/xtunnel/xtunnel` |
| Служба | `/etc/systemd/system/xtunnel-app.service`; шаблон в [`deploy/xtunnel-app.service`](../deploy/xtunnel-app.service) |
| Цель и тайм-аут | `127.0.0.1:8083`, `--backend-timeout 120` |
| Автозапуск | `Restart=always`, `RestartSec=10`, запуск при загрузке VM |
| Лицензия xTunnel | `XTUNNEL_LICENSE` в `/home/dariamishina/.local/share/xtunnel/license.env`, права `0600`; явный выбор `--license` |
| URL в `.env` API | `APP_API_PUBLIC_URL` уже обновлён на постоянный адрес без `/v1` |
| URL в Android | Тот же адрес с завершающим `/` задан по умолчанию в `android/data/build.gradle.kts` и встроен в актуальный debug APK |

Проверка на VM:

```bash
systemctl is-active app-api xtunnel-app
systemctl is-enabled app-api xtunnel-app
curl -fsS --max-time 10 http://127.0.0.1:8083/health
curl -fsS --max-time 20 https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com/v1/docs
```

Ожидаются `active` и `enabled` для обеих служб, `OK` локально и JSON API снаружи. Публичный `/health` перенаправляется на `/health/live` самого xTunnel и не подтверждает работу App API. Для перезапуска туннеля: `sudo systemctl restart xtunnel-app`; терминал после этого держать открытым не нужно.

В APK проверены новый URL в DEX, отсутствие прежнего тестового адреса и действительная debug-подпись v2. 20 сентября APK установлен на телефон, а полный серверный smoke-сценарий с DeepSeek пройден через xTunnel. На телефоне остаются проверки долгого ответа, обрыва сети и безопасного повтора.

### На проде

- Поддерживать купленную лицензию **Личный** активной; текущий срок — до **19.10.2026**. Продление ещё не выполнено.
- Проверить этот же постоянный URL в release-сборке; webhook ЮKassa для приложения настроить на этапе 5.
- Пройти полный сценарий с DeepSeek, включая долгий ответ, и пользовательскую приёмку: доступный `/v1/docs` не заменяет эти проверки.
- Ключ xTunnel хранится только в серверном `license.env`; секреты API — в серверном `.env`, секреты CI при необходимости — в GitHub Secrets. Значения ключей не включать в документы, код и APK.
