# План: Android-приложение «Сфера Таро» (только RuStore)

Отдельное приложение для Android на базе логики чат-бота в Max. Бот **не ломаем** и **не связываем** с приложением в первой версии.

Приложение — не окно в Max и не сайт в браузере, а обычная программа с иконкой на телефоне. Ставят из **RuStore**.

## Зафиксированные решения

| Вопрос | Решение |
|--------|---------|
| Отображаемое название и название в RuStore | **Сфера Таро** |
| `applicationId` / package name | Прод и его магазинная альфа: **`ru.tarotsphere.app`**; отдельный локальный тест: **`ru.tarotsphere.app.test`** |
| Платформа | Только Android |
| Язык приложения | Kotlin + Jetpack Compose |
| Магазин | Только **RuStore** (Google Play — не делаем) |
| Оплата в приложении | Сначала **RuStore Pay SDK**; **ЮKassa** отложена до публикации приложения и открытия магазина |
| База данных | **Отдельная** PostgreSQL, не таблица бота |
| Регистрация | Обязательна перед первым раскладом: обычные логин/пароль, VK ID или одноразовый email-код |
| Основной вход | Логин/пароль, вкладки «Вход» и «Регистрация». VK ID и email-код — другие способы. Восстановление пароля — через заранее подтверждённую почту в профиле |
| Идентификация устройства | `ANDROID_ID` только как дополнительный антифрод-сигнал, не как аккаунт и не как единственный способ входа |
| Дополнительные входы позже | Яндекс ID — не в первой production-версии |
| Связка с аккаунтом бота Max | **Не делаем** (бэклог) |
| iOS / Flutter | Не делаем |
| HTTPS для API приложения | **[xTunnel](https://xtunnel.ru/)** — свой домен **не покупаем**. Пользователи URL **не видят** |
| Cloudflare | Только для **WebApp** бота (порт 8081). Для Android **не обязателен** |

Бот в Max живёт как сейчас: свои пользователи, свой баланс, своя ЮKassa. Покупка в боте **не** появится в приложении, и наоборот. Это ожидаемо, пока нет связки.

### Схема использования сборок

| Вариант | Package / сервер | Назначение и установка |
|---|---|---|
| Отдельный тест | `ru.tarotsphere.app.test` / staging | Ежедневная проверка дизайна и функций; APK вручную рядом с продом; отдельные аккаунты, история и баланс |
| Прод | `ru.tarotsphere.app` / production | Обычное использование, преимущественно через RuStore; допустима ручная установка корректно подписанного release APK |
| Альфа основного приложения | `ru.tarotsphere.app` / сейчас staging по release-gate проекта | Закрытое тестирование через RuStore по необходимости; в одном профиле Android заменяет прод, а не устанавливается рядом |

**Окружение, тип сборки и канал распространения — разные вещи.** Staging/production определяют сервер, данные и интеграции; debug/release — отладку и подпись; APK вручную/альфа/RuStore-релиз — способ доставки. Полноценный тест может быть release-сборкой. Сейчас отдельный тест реализован через debug suffix, а не через полноценные flavors `staging`/`production`; выделение `stagingRelease` с постоянной тестовой подписью — дальнейший шаг для интеграционной приёмки.

На основном телефоне достаточно **теста и прода**. Постоянно поддерживать третью альфа-установку не нужно. Альфа полезна перед релизом для проверки магазинной установки/обновления и выдачи сборки закрытому кругу тестировщиков; при необходимости использовать другой телефон или профиль Android. Альфа сама по себе не включает sandbox-платежи и не выбирает сервер. В текущем проекте `alpha` явно требует staging URL; такой артефакт нельзя без пересборки продвигать в production, иначе он останется подключён к staging.

Удаление APK с телефона не исключает аккаунт из альфа-группы. Проверить участие в RuStore Консоли: при сохранённом доступе магазин может показывать альфа-версию приоритетнее стабильной.

Тест и прод можно устанавливать вручную; прод также распространять через RuStore. Для обновления одной установки нужны одинаковые `applicationId` и совместимая подпись, а `versionCode` не должен быть ниже установленного. Это одна продовая установка, а не две копии по источникам. Ручная установка версии с кодом выше магазинного откладывает обычное обновление из магазина до появления подходящей версии; обычный downgrade поверх установленного приложения не поддерживается. Для новых публикаций повышать `versionCode` выше уже загруженных версий. Продовый keystore сохранять; для будущего постоянного тестового контура завести собственный стабильный ключ, не полагаться на случайный debug-keystore разных машин.

### VK ID в отдельном тесте: почему выключен и как включить

Отключение временное и относится только к новому `.test` APK, а не ко всем тестовым сборкам. Старые интеграционные проверки альфы не означают, что VK ID настроен для нового package. При одинаковом VK client ID схема возврата `vk{client_id}` совпадает у двух установок: результат авторизации может попасть не в то приложение.

- [ ] Создать отдельное подключение приложения в кабинете VK ID для тестового контура; настроить package `ru.tarotsphere.app.test` и параметры подписи согласно требованиям кабинета.
- [ ] Настроить тестовые client ID, параметры SDK и отдельную схему возврата; согласовать их с проверкой VK-авторизации на staging API. Production-параметры не заменять тестовыми.
- [ ] Вернуть SDK/redirect receiver, кнопку входа и привязку VK только после настройки; одного `VK_AUTH_ENABLED=true` недостаточно.
- [ ] На телефоне с одновременно установленными тестом и продом проверить вход, отмену, повторный вход и привязку; callback должен попадать в правильное приложение, данные — только в нужное окружение.

До выполнения доступны тестовые логин/пароль и email-код. Наличие production-аккаунта не создаёт автоматически staging-аккаунт и не переносит его баланс/историю.

### Покупки в отдельном тесте: почему выключены и как включить

RuStore Pay требует совпадения package и подписи с приложением, зарегистрированным в консоли. Новый `.test` нельзя подключить к production-карточке простой заменой флага. Текущий APK позволяет смотреть магазин, но не проверять оплату; ранее проверенные sandbox-покупки относятся к старой магазинной альфе.

- [ ] Для независимого теста зарегистрировать отдельное приложение `.test` в RuStore Консоли, согласовать доступность монетизации, настроить тестовые товары/подписки и пройти модерацию хотя бы первой версии.
- [ ] Настроить постоянную тестовую подпись и matching package, отдельный Console App ID и корректную Pay deeplink-схему; восстановить инициализацию SDK и кнопки оплаты после настройки.
- [ ] Подключить соответствующие платёжные настройки, серверную проверку и уведомления к staging. Не смешивать production и staging ключи, webhook-маршруты, базы и начисления. Серверные секреты не помещать в APK.
- [ ] Добавить нужный аккаунт в тестировщики платежей выбранного приложения и явно включить ему тестовый режим в RuStore Консоли. На телефоне установить RuStore и войти под этим VK ID.
- [ ] Перед оплатой проверить отметку **«Тестовая покупка»**. Без неё не продолжать: покупка может быть реальной. Само название «тест», debug или участие в альфе бесплатность оплаты не гарантирует.
- [ ] Повторить сквозные сценарии: успешная/неуспешная оплата, начисление ровно один раз, повторная verify, восстановление, возврат, оформление/продление/отмена подписки. Возможности sandbox и серверной проверки подписок сверять с актуальной документацией SDK перед приёмкой.

Альтернатива отдельной интеграции — проверять зарегистрированное основное приложение в закрытой альфе с включённым для тестировщика sandbox на отдельном устройстве/профиле. Это не даёт одновременные альфу и прод в одном профиле и не заменяет настройку независимого `.test`.

### Ближайшие действия

1. Проверить дизайн и основные сценарии нового тестового APK на телефоне; не удалять прод ради этой проверки.
2. Настроить отдельные VK ID и RuStore интеграции по чек-листам выше, если требуется полноценная ежедневная интеграционная приёмка рядом с продом. Это ещё не выполнено и требует действий в кабинетах провайдеров.
3. Перед магазинным релизом отдельно проверить release-подпись, API URL, канал, `versionCode`, установку/обновление и платежи; использовать альфу по необходимости. Пересобирать кандидат с production URL, не переносить staging-артефакт в публичный релиз.
4. Продолжать работу по [ANDROID_ENVIRONMENTS.md](ANDROID_ENVIRONMENTS.md) и [ANDROID_BUILD.md](ANDROID_BUILD.md). Коммит, push, публикацию и изменения внешних кабинетов не считать выполненными без отдельного подтверждения.

Источники для перепроверки требований: [VK ID SDK и redirect scheme](https://github.com/VKCOM/vkid-android-sdk), [требования RuStore Pay к package и подписи](https://www.rustore.ru/help/sdk/pay/kotlin-java/11-2-0), [включение тестовых платежей](https://www.rustore.ru/help/developers/monetization/sandbox/enable-test-mode), [проверка Pay SDK](https://www.rustore.ru/help/developers/monetization/sandbox/testing-sdk-pay), [приоритет тестовых версий RuStore](https://www.rustore.ru/help/users/app-management/testing), [правила обновления Android](https://developer.android.google.cn/google/play/app-updates?hl=en).

### 2.3. Кто такой пользователь приложения

В Max идентификатор даёт мессенджер. В Android создаётся собственный `user_id` с идентификатором логина/пароля либо подтверждённым VK ID/email. Произвольный логин не означает подтверждённую почту.

После онбординга показывается единый экран **«Войти или создать аккаунт»**:

- основной экран — **«Вход по логину и паролю»**, вкладки «Вход» и «Регистрация»;
- через «Другие способы» доступны VK ID и email с одноразовым кодом;
- для парольной регистрации нужны уникальный логин, пароль и его подтверждение;
- парольный вход не требует писем; для восстановления нужно заранее подтвердить почту в профиле. «Забыли пароль?» позволяет сменить пароль по одноразовому коду.

| Когда | Что происходит |
|-------|----------------|
| Новый логин, VK ID или подтверждённый email | Создаётся аккаунт; подарок выдаётся через `trial_claims` с проверкой идентификатора и устройства |
| Повторный вход | Открывается тот же `user_id`, баланс и история сохраняются |
| Новый телефон | Вход тем же логином/паролем, VK ID или email-кодом открывает прежний аккаунт |
| Добавлен второй способ из профиля | Привязка VK ID реализована; почта восстановления не является привязкой email-входа. Обратная привязка email-входа остаётся в бэклоге |
| После выхода выбран другой, ещё не привязанный способ | Создаётся или открывается другой аккаунт; автоматического объединения по устройству нет, потому что `ANDROID_ID` не является доказательством владения аккаунтом |
| Выход | Локальные токены очищаются, серверные баланс и история остаются |
| Удаление аккаунта | Пользовательские данные удаляются; повторная регистрация не должна автоматически возвращать пробный подарок |

Текущий автоматический `/auth/guest` нужен только для существующей debug-версии и тестового перехода. В production новый анонимный гость не получает баланс и не может выполнять расклады или покупки.

## 3. API приложения

Префикс API: `https://01a0ba9c-b091-79dc-9a97-07e3b1eba847.tunnel4.com/v1/`. В `APP_API_PUBLIC_URL` серверного `.env` и `BuildConfig.API_BASE_URL` Android задаётся адрес без `/v1`; пути методов добавляет клиент.

Отдельный процесс, например `app_api_server.py`, порт не 8081 (у бота webhook). Не смешивать с `bot.py`.

Access-токен обязателен для запросов к данным пользователя. Исключения: начало/подтверждение входа, обновление сессии, псевдонимное событие запуска `/telemetry/app-open`, `/health`, `/v1/docs` и изображения `/static/`. `user_id` определяется только из проверенного сервером токена.

**Статус API на 2026-10-22:** методы MVP, VK ID, email-код, логин/пароль, восстановление и RuStore Pay развёрнуты на staging и доступны через постоянный xTunnel. Миграции 004–011 применены. Вход, восстановление данных и пароля, покупки, подписка и возврат проверены из альфы RuStore. Гостевой сценарий остаётся только для тестирования; RuStore Push, Ицзин и карта дня ещё не реализованы.

| Метод | Путь | Зачем |

`/auth/guest` временно сохраняется только в staging для проверки уже реализованного приложения. Перед production он не должен выдавать пробный баланс анонимному запросу.

Для email-кода: 6 цифр, срок действия 10 минут, одно использование, не больше 5 попыток ввода; повторная отправка не раньше чем через 60 секунд. Нужны лимиты по email, IP и сигналу устройства. Коды и полные адреса не писать в журналы.

Для VK ID приложение получает результат официального SDK и передаёт его серверу; сервер проверяет токен у провайдера и только затем доверяет `provider_user_id`. Не принимать VK ID обычной строкой из тела запроса.

Правило связывания: один `provider_user_id` принадлежит только одному `user_id`. Если идентификатор уже занят другим аккаунтом, показать ошибку и не объединять балансы автоматически. Для текущих тестеров первый подтверждённый вход может преобразовать существующего staging-гостя в аккаунт без потери истории; в чистом production аккаунт создаётся только после подтверждения VK ID или email.

**Нет** `/auth/link/max`. Яндекс ID и Google-вход в первую production-версию не входят.

### 4.1. `app_users`

Сервер создаёт пользователя после подтверждения VK ID или email:

- `user_id` UUID
- `is_guest` — `false` для production-аккаунтов; `true` остаётся только у старых staging-гостей на время перехода
- `created_at`, `last_active_at`
- `install_id` — старый случайный идентификатор debug-версии, не использовать как доказательство уникального пользователя

Идентификаторы хранятся в `app_user_identities`; логин и scrypt-хеш пароля — в `app_password_credentials` (миграция `007_password_auth.sql`). Открытые пароли не сохраняются.

### 4.1.1. `app_user_identities`

Один пользователь — несколько способов входа.

- `user_id`
- `provider`: в первой версии `vk` | `email`; позже можно добавить `yandex`
- `provider_user_id`: проверенный VK ID или нормализованный email
- `verified_at`, `created_at`
- UNIQUE (`provider`, `provider_user_id`) — один VK ID или email не должен принадлежать двум аккаунтам

Исходный вид email можно хранить для отображения и отправки кодов, а сравнение выполнять по единой заранее зафиксированной нормализации. В API и журналах адрес маскировать.

### 4.1.2. `app_email_codes`

Короткоживущие запросы входа по email:

- нормализованный email;
- хеш одноразового кода, но не сам код;
- срок действия, число попыток, время следующей разрешённой отправки;
- `used_at`, IP/риск-метаданные в минимально необходимом объёме;
- просроченные и использованные записи регулярно удаляются.

### 4.1.3. `app_trial_claims` и устройство

- Пробный пакет выдаётся только после первого подтверждённого входа.
- Один `user_id` получает 3 бесплатных расклада только один раз.
- Дополнительный ключ устройства строится на сервере как HMAC от `ANDROID_ID`; исходный идентификатор не используется как токен авторизации.
- Один и тот же аккаунт на новом телефоне восстанавливает старый баланс, но не получает новый подарок.
- Новый аккаунт на устройстве, уже получившем подарок, по умолчанию не получает второй пакет. Возможные ложные блокировки общего семейного телефона обрабатываются поддержкой.
- `ANDROID_ID` — только антифрод-сигнал: он не заменяет VK ID/email и не даёт доступа к аккаунту.
- Email и VK ID независимы: провайдеры не сообщают общий надёжный идентификатор человека. Сервер не может безопасно определить, что несколько почт и несколько VK ID принадлежат одному владельцу, и не объединяет их автоматически.
- Ограничение «один подарок на устройство» снижает простую накрутку, но не гарантирует «один подарок на человека»: несколько реальных устройств, профили Android, сброс устройства и набор независимых идентификаторов оставляют остаточный риск.
- Если стоимость злоупотреблений станет заметной, усиливать защиту слоями: лимиты по IP/устройству и скорости регистраций, журнал причин отказа, сигналы целостности устройства; более сильный общий признак — подтверждённый телефон или платёжный инструмент — вводить только после оценки влияния на конверсию и приватность.

### 4.2. `app_user_balances`

Как у бота по смыслу: бесплатные, купленные, дата безлимита. Новый баланс начинается с **0**; допустимый первый вход/регистрация через `trial_claims` транзакционно начисляет **3 бесплатных**. Повторный идентификатор или сигнал устройства не получает подарок. Одновременная смена обоих сигналов остаётся ограничением антифрода; это не доказательство уникальности человека.

### 4.3. `app_payments`

История: пакет, сумма, статус, `provider` (`rustore` | `yookassa`), внешний id платежа.

### 4.4. `app_divinations`

Вопрос, карты, толкование, дата. На этапе 4 добавлены `request_id` для безопасного повтора и `follow_ups` для уточнений. Эти поля появятся на действующем сервере после применения `app/migrations/004_mvp.sql`.

Обратная связь хранится в новой таблице **`app_feedback`** из той же миграции. Удаление аккаунта удаляет связанные пользовательские данные; отдельно определить минимальный срок хранения платёжных и антифрод-записей и описать его в политике.

### 4.5. `app_devices`

Токен пуша RuStore, пользователь/сессия и серверный HMAC от `ANDROID_ID` для антифрода. Исходный `ANDROID_ID` не хранить и не считать идентификатором аккаунта.

### 4.6. Чего нет в MVP

- Яндекс ID и входа через Max
- Таблиц связки с Max
- Кодов `/link`
- Записи в `max_users` / `max_user_balances`

- Следующий production-кандидат обязательно проходит отдельный закрытый тест, потому что в нём будут production API URL, `APP_RUSTORE_SANDBOX=false` и, возможно, ссылки на документы. Непроверенный новый бинарник напрямую публично не выпускается.

- прогнать серверные unit/integration-тесты покупки, повторной verify, callback и возврата;

- Общая БД с ботом

## 8. Безопасность

1. Ключи DeepSeek, ЮKassa, секреты RuStore — только на сервере.
2. HTTPS + access/refresh-токены; `user_id` только из проверенного токена, не из тела запроса.
3. VK-токен проверяется сервером у провайдера; email-код одноразовый, короткоживущий и ограничен по попыткам.
4. Пароли храним только как scrypt-хеш с индивидуальной солью; открытые пароли, коды, токены и полные email не пишем в журналы.
5. Списание баланса и выдача пробного пакета только на сервере и транзакционно.
6. Один внешний id платежа — одно начисление.
7. Вебхук ЮKassa бота и вебхук приложения — разные URL и разные БД.
8. Удаление аккаунта и отзыв всех его сессий из профиля.
9. `ANDROID_ID` — дополнительный антифрод-сигнал, а не секрет или способ авторизации.

## 14. HTTPS для API: xTunnel (без своего домена)

### Зачем это вообще

Приложение на телефоне **звонит на ваш сервер** по адресу `https://...`. Нужны:

1. **HTTPS** — иначе Android и оплата не работают нормально.
2. **Один и тот же адрес** — не меняется после перезапуска (для APK и webhook ЮKassa).

**Красивый домен пользователям не нужен** — URL вшит в код, в интерфейсе не показывается.

### Cloudflare — отдельная история

| | WebApp бота (браузер) | Android-приложение |
|--|----------------------|-------------------|
| Сейчас | Quick tunnel Cloudflare → порт **8081** | **Не используем** |
| Нужен Cloudflare? | Можно оставить как есть | **Нет** |

К Cloudflare **не привязаны**. Для приложения — **xTunnel**.

### Купленная лицензия xTunnel

19 сентября приобретена **Личная лицензия на месяц за 150 ₽**. Регистрация клиента на сервере подтвердила тариф **Personal**; 22 октября лицензия продлена до **19.11.2026**.

Свой домен у регистратора **не покупаем**: используется постоянный адрес xTunnel (`*.tunnel4.com`). Перед окончанием оплаченного периода нужно продлить лицензию для дальнейшей работы туннеля.

### Схема на VM

```
Android  →  https://....tunnel4.com/v1/...
                ↓
           xTunnel (на VM)
                ↓
      http://127.0.0.1:8083  ← app_api_server.py
                ↓
           app_bot_db
```

Порт **8083** — API приложения (`APP_API_PORT`). Порт **8081** — webhook бота / WebApp. Порт **8080** — psy_max.

### Текущая настройка туннеля (проверено 2026-09-19)

Базовый API проверен через постоянный HTTPS-адрес с Mac и с VM. После перезапуска туннеля адрес сохранился, внешний `/v1/docs` вернул тот же JSON, что локальный API. Обновление кода этапа 4 и миграция в ходе настройки туннеля не выполнялись.

Проверка на VM:

```bash
systemctl is-active app-api xtunnel-app
systemctl is-enabled app-api xtunnel-app
```

Ожидаются `active` и `enabled` для обеих служб, `OK` локально и JSON API снаружи. Публичный `/health` перенаправляется на `/health/live` самого xTunnel и не подтверждает работу App API. Для перезапуска туннеля: `sudo systemctl restart xtunnel-app`; терминал после этого держать открытым не нужно.

В APK проверены новый URL в DEX, отсутствие прежнего тестового адреса и действительная debug-подпись v2. 20 сентября APK установлен на телефон, а полный серверный smoke-сценарий с DeepSeek пройден через xTunnel. На телефоне остаются проверки долгого ответа, обрыва сети и безопасного повтора.
