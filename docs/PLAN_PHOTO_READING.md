# Распознавание карт по фото / текстовый ввод карт

## Текущее состояние

- **Модель:** `deepseek-flash` (актуальный алиас V4.1 Flash; обновлено 26.09.2026).
- **Vision:** Не используется. DeepSeek V4-Pro и V4-Flash нативно поддерживают мультимодальный ввод (текст + изображения) через тот же endpoint.
- **Входящие фото:** Бот не обрабатывает фото от пользователей — все хендлеры работают только с `message.content` (текст).
- **Пайплайн гадания:** Вопрос → выбор карт (рандом / WebApp) → имена и значения отправляются текстом в DeepSeek → ответ → follow-up.

---

## Два сценария

### А. Текстовый ввод названий карт

Пользователь пишет: «Башня, Туз Кубков, Десятка Мечей» → бот парсит → расклад.

- **Сложность:** Низкая
- **Не требует vision** — работает на текущей модели
- **Риски:** опечатки, сокращения, разные варианты названий

### Б. Распознавание карт по фото

Пользователь фотографирует физические карты → DeepSeek V4 распознаёт → расклад.

- **Сложность:** Средняя
- **Требует vision** (DeepSeek V4)
- **Риски:**
  - Качество фото (освещение, угол, размытие)
  - Разные колоды (Rider-Waite, авторские) — LLM может не узнать карту
  - Перевёрнутые карты — сейчас бот не работает с реверсами
- **Стоимость:** V4-Flash: $0.14/M входных токенов, ~90 KV-cache entries на изображение

### Этап 2: Распознавание карт по фото

#### 2.0. Монетизация и баланс

**Решение:** Фото-расклад = 1 обычный расклад (единая «валюта»).

- Не вводим отдельные платежи или пакеты за фото-распознавание
- Списывается 1 расклад с баланса — как рандом или WebApp
- В безлимите (599₽/мес) фото-расклады входят без ограничений
- Фото доступно всем пользователям (включая бесплатных — 3 бесплатных расклада любым методом)
- Если себестоимость vision станет проблемой — в будущем можно переключить на «2 расклада за фото»

**Обоснование:** Пользователю непонятно, зачем два типа раскладов стоят по-разному, если результат одинаковый. Единый баланс = простой UX.

#### 2.1. Размещение в боте (UX)

**Решение:** Кнопка «📸 Сфотографировать расклад» внутри таро-флоу с визуальной группировкой.

Текущие кнопки после вопроса перегруппируются:

```
Ваш вопрос: «...»

Выберите способ гадания:

• 🔮 Карты покажут сами — случайный расклад
• 🃏 Выбрать карты самой — красивый интерфейс выбора

Или используйте свои карты:
• 📸 Сфотографировать расклад
• ✍️ Написать названия карт
```

**Обоснование:** Вопрос уже задан — пользователь выбирает *как получить карты*. Фото — просто ещё один метод. Две логические группы («бот тянет» vs «свои карты») снимают ощущение перегруженности. Не нужно менять главное меню и не нужна отдельная точка входа.

**Изменения в коде (`_do_tarot_divination`):**
- [ ] Перегруппировать кнопки: сначала «рандом» + «WebApp», затем разделитель-текст, затем «фото» + «текст»
- [ ] Новый callback: `"tarot_photo"` → переход в `STATE_WAITING_FOR_PHOTO`
- [ ] Обновить описание кнопок в сообщении

#### 2.2. Обработка входящих фото в aiomax

- [ ] Изучить как aiomax передаёт вложения (`message.attachments` / аналог)
- [ ] Хендлер для фото в FSM-состоянии `waiting_for_photo`
- [ ] Скачивание фото по URL из MAX API

#### 2.3. Промпт для распознавания

- [ ] Двухэтапный подход:
  1. **Распознавание:** фото → DeepSeek V4 vision → JSON с названиями карт
  2. **Интерпретация:** сопоставление с `TAROT_CARDS` → обычный пайплайн толкования
- [ ] Промпт распознавания: «На фото расклад карт Таро. Определи каждую карту слева направо. Верни JSON: `[{"position": 1, "card": "название"}, ...]`»
- [ ] Формат vision-запроса: `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}`
- [ ] `max_tokens` для vision-распознавания: ~100 (только JSON, без толкования)

#### 2.4. Сопоставление с колодой

- [ ] Маппинг английских названий от LLM к ключам `TAROT_CARDS`
- [ ] Fuzzy matching на случай вариаций
- [ ] Fallback: если карта не распознана → попросить ввести название вручную

#### 2.5. UX-флоу

```
Вопрос → выбор «📸 Сфотографировать расклад»
→ бот: «Сфотографируй свой расклад (3 карты) и пришли фото 📸»
→ пользователь отправляет фото
→ бот: «Распознаю карты...» (typing indicator)
→ бот: «Я вижу: 1. Башня, 2. Туз Кубков, 3. Десятка Мечей. Верно?»
   [✅ Да, всё верно] [✏️ Исправить]
→ пользователь: «Да» → толкование через обычный пайплайн
→ пользователь: «Исправить» → переход в STATE_WAITING_FOR_CARDS_INPUT (текстовый ввод)
```

#### 2.6. Обработка ошибок

- [ ] Фото без карт → «Не могу распознать карты на этом фото. Попробуй сфотографировать ещё раз — положи карты на ровную поверхность при хорошем освещении»
- [ ] Не то количество карт → «Я вижу N карт, а нужно 3. Сфотографируй именно 3 карты или напиши их названия»
- [ ] Таймаут vision-запроса → retry (1 раз), затем fallback: «Не удалось распознать. Напиши названия карт текстом»
- [ ] Не фото (стикер, документ и т.д.) → «Пришли именно фото карт»

**Оценка:** ~8–12 часов

## Потенциальные расширения (не в первой версии)

- **Произвольное количество карт:** не ограничивать тремя — пользователь фотографирует Кельтский крест, 5 карт и т.д. (нужен адаптивный промпт интерпретации)
- **Перевёрнутые карты:** поддержка реверсов (усложнит логику, но повысит ценность)
- **Одноэтапное толкование:** отправить фото + вопрос в один запрос с промптом «определи карты и дай толкование» (проще, но меньше контроля)
