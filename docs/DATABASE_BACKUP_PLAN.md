# План резервного копирования PostgreSQL

## Цель

Настроить автоматическое резервное копирование всех рабочих PostgreSQL-баз с VM
`46.16.36.243` во внешнее S3-совместимое хранилище. Потеря VM или ее диска не
должна приводить к потере резервных копий.

## Базы данных в контуре

| База | Приложение | Размер на 2026-10-08 |
|---|---|---:|
| `max_bot_db` | MAX-бот | 84 МБ |
| `app_bot_db` | Android API | 9,7 МБ |
| `psy_bot_db` | Psy Max | 97 МБ |
| `girl_bot_db` | Girl Max | 26 МБ |

Общий несжатый размер одного комплекта — около 217 МБ. Формат `pg_dump -Fc`
использует сжатие, поэтому фактический размер комплекта должен быть меньше.

## Целевая схема

1. На VM запускается root-owned systemd service.
2. Для каждой базы выполняется отдельный согласованный дамп:
   `pg_dump --format=custom --no-owner --no-acl`.
3. Каждый архив проверяется командой `pg_restore --list`.
4. Формируется manifest с именами файлов, временем создания, версией PostgreSQL,
   размерами и SHA-256.
5. Файлы шифруются до отправки публичным ключом `age`. Приватный ключ хранится
   вне VM, в менеджере паролей и резервной копии владельца.
6. Зашифрованные файлы загружаются в приватный bucket VK Cloud Object Storage.
7. После загрузки проверяются наличие и размер удаленных объектов.
8. Локальные временные файлы удаляются только после успешной проверки загрузки.

## Расписание и хранение

- Запуск: ежедневно в 03:00 MSK.
- Оркестрация: `postgres-backup.service` и `postgres-backup.timer`.
- Для timer установить `Persistent=true`, чтобы пропущенный запуск произошел
  после включения VM.
- Целевое хранение: три последних успешных комплекта каждой базы.
- Объекты получают уникальные имена с UTC-временем, например:
  `daily/max_bot_db/2026/10/08/max_bot_db-20261008T000000Z.dump.age`.
- У серверного S3-ключа есть права только на загрузку и проверку объектов, без
  удаления и изменения bucket configuration.
- Удаление архивов старше четырех суток выполняет lifecycle policy bucket.
  Из-за времени выполнения lifecycle в bucket кратковременно может находиться
  четвертый комплект; это безопаснее, чем случайно оставить только две копии.

При ежедневном расписании RPO составляет до 24 часов. Если потеря платежей и
пользовательских данных за сутки станет неприемлемой, timer переводится на запуск
каждые шесть часов без изменения остальной схемы.

## VK Cloud Object Storage

- Отдельный аккаунт или проект, не связанный с учетными данными VM.
- Приватный bucket без публичного доступа.
- S3 endpoint и имя bucket задаются в root-only конфигурации на VM.
- Отдельный service account/access key для backup job.
- Входящие dump-файлы уже зашифрованы на стороне VM; серверное шифрование
  хранилища можно включить дополнительно.
- Billing alerts должны предотвращать остановку или удаление хранилища из-за
  исчерпания баланса.

## Файлы реализации

Планируемые файлы в репозитории:

- `scripts/backup_databases.sh` — создание, проверка, шифрование и загрузка;
- `deploy/postgres-backup.service` — одноразовый systemd unit;
- `deploy/postgres-backup.timer` — ежедневный timer;
- `deploy/backup.env.example` — шаблон root-only конфигурации;
- `scripts/restore_database_backup.sh` — контролируемое восстановление;
- обновление `.env.example` только именами переменных, без секретов.

Эти файлы реализованы. До включения production timer остаются внешние шаги:
создание bucket, S3-ключа, ключа `age` и первое полное тестовое восстановление.

Секреты не коммитятся. На сервере они размещаются, например, в
`/etc/max-bot-backup/backup.env` с владельцем `root:root` и правами `0600`.
Это отдельная конфигурация backup-сервиса: переменные не должны находиться в
`/home/dariamishina/max_bot/.env` или в основном `.env.example` приложения.

Каталог `/etc/max-bot-backup` имеет владельца `root:root` и права `0700`, поэтому
обычный пользователь не может выполнить `cd` в него. Для проверки метаданных и
редактирования используются:

```bash
sudo ls -la /etc/max-bot-backup
sudoedit /etc/max-bot-backup/backup.env
```

`sudo cd ...` не работает, поскольку `cd` является встроенной командой shell.
Если необходима root-сессия, используется `sudo -i`, но для единичного изменения
безопаснее `sudoedit`.

## Контроль успешности

Каждый запуск считается успешным только если:

1. дампы созданы для всех четырех баз;
2. `pg_restore --list` успешно прочитал каждый архив;
3. SHA-256 manifest создан;
4. все четыре зашифрованных файла загружены;
5. удаленное хранилище подтвердило наличие объектов ожидаемого размера.

При ошибке systemd unit завершается с ненулевым кодом и отправляет уведомление
администратору. Отсутствие успешного backup heartbeat дольше 26 часов также
считается аварией.

## Проверка восстановления

- После каждого backup выполняется структурная проверка архивов.
- Раз в месяц последний комплект скачивается именно из VK Cloud,
  расшифровывается и восстанавливается во временные базы.
- Проверяются наличие основных таблиц и контрольные количества строк.
- Результат restore test фиксируется с датой, длительностью и именами объектов.

## Порядок внедрения

1. Создать приватный bucket и lifecycle policy во VK Cloud.
2. Создать ограниченный S3 access key.
3. Создать offline-ключ `age` и сохранить приватную часть вне VM.
4. Реализовать и локально проверить backup/restore scripts.
5. Установить конфигурацию и systemd units на VM.
6. Выполнить ручной запуск и проверить четыре объекта в bucket.
7. Выполнить тестовое восстановление всех четырех баз.
8. Включить timer и мониторинг отсутствия свежего backup.

### Установка на VM после создания bucket и ключей

```bash
sudo apt-get update
sudo apt-get install -y age awscli

sudo install -d -m 0700 /etc/max-bot-backup
sudo install -m 0600 deploy/backup.env.example /etc/max-bot-backup/backup.env
sudo nano /etc/max-bot-backup/backup.env

sudo install -m 0755 scripts/backup_databases.sh /usr/local/sbin/max-bot-db-backup
sudo install -m 0755 scripts/restore_database_backup.sh /usr/local/sbin/max-bot-db-restore
sudo install -m 0644 deploy/postgres-backup.service /etc/systemd/system/
sudo install -m 0644 deploy/postgres-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload

# Первый запуск и проверка до включения расписания.
sudo systemctl start postgres-backup.service
sudo systemctl status postgres-backup.service --no-pager
sudo journalctl -u postgres-backup.service -n 100 --no-pager

# Включать только после успешного ручного запуска и restore test.
sudo systemctl enable --now postgres-backup.timer
systemctl list-timers postgres-backup.timer --no-pager
```

## Отдельная задача безопасности

PostgreSQL сейчас слушает `0.0.0.0:5432`, а UFW на VM выключен. До внедрения
или одновременно с ним нужно проверить внешние зависимости, после чего:

- привязать PostgreSQL к `127.0.0.1`, если удаленные клиенты не нужны;
- закрыть TCP 5432 в firewall облачного провайдера;
- включить host firewall;
- пересмотреть правила `pg_hba.conf`.

Эта задача не заменяет резервное копирование, но снижает вероятность компрометации
самой базы.
